Plan de despliegue en Vercel

Frontend React + Tailwind (Bento Grid) consumiendo el backend Express ya construido, todo en un solo proyecto Vercel. El Express se porta a funciones serverless bajo /api; Supabase queda detrás del backend con la service_role key.

1 repo

Un solo proyecto, un solo deploy. Se elimina el .git anidado del backend.

13

endpoints reales del backend que el frontend consumirá vía /api/*.

5

pantallas: catálogo, detalle, login/registro, carrito (batch), wishlist.

Frontend

React 19 + Vite 8 + Tailwind. Estética Bento Grid / neominimal. Guarda access_token en localStorage y manda Bearer.

Backend

Express → api/index.js serverless. Rutas montadas bajo /api. Sin app.listen en producción.

Arquitectura objetivo

Navegador (React SPA) │ fetch ${BASE}/api/... BASE = '' en prod · http://localhost:3000 en dev ▼ ┌─────────────────────────────────────────────┐ │ PROYECTO ÚNICO EN VERCEL │ │ │ │ / → build estático de Vite │ │ /api/* → api/index.js (Express) │ ← serverless, lee env vars └───────────────────────┬──────────────────────┘ │ service_role key (solo servidor) ▼ Supabase (Postgres + Auth + Storage) tablas: garments · garment_states · cart_items · wishlist

Clave: la service_role key vive solo en las variables de entorno de Vercel (lado servidor). El navegador nunca la ve. Por eso todo dato pasa por el backend — el frontend no habla con Supabase directamente y no necesita la anon key.

Avisos antes de empezar

Dependencias al raíz. Vercel instala dependencias desde el package.json de la raíz. Hoy express, cors, @supabase/supabase-js y multer solo están en backend/package.json. Hay que moverlas/duplicarlas al package.json raíz o la función serverless fallará al importar.
Estados reales ≠ documento del proyecto. El documento dice disponible/rentada/en evaluación/esterilizada/vendida, pero el código usa available · reserved · rented · in_cleaning · retired. El frontend debe seguir al backend. Cambiar a español es otra tarea (tocar BD + backend primero).
Bucket de Storage. El endpoint /upload sube al bucket garments de Supabase Storage. Debe existir y ser público para que las imágenes se vean en el catálogo.

Fases

0

Consolidar el repositorio

  • Eliminar backend/.git para que sea un solo repo versionado.
  • Confirmar que backend/.env sigue en .gitignore. La service_role key jamás se commitea.
1

Frontend React + Tailwind (Bento Grid)

  • Instalar y configurar Tailwind sobre el proyecto Vite existente.
  • Cliente API (wrapper fetch) que lee VITE_API_URL y adjunta el Bearer.
  • Contexto de auth: guardar access_token en localStorage, login/logout, rutas protegidas.
  • Router con 5 vistas: Catálogo, Detalle (+ historial de estados), Login/Registro, Carrito/Batch, Wishlist.
  • Sistema visual Bento Grid / neominimal aplicado a catálogo y tarjetas de prenda.
2

Portar el Express a serverless

  • Extraer la app a un módulo reutilizable (sin app.listen en serverless).
  • Montar todas las rutas bajo /api (/api/garments, /api/auth/login, …).
  • Crear api/index.js que exporte la app por default.
  • vercel.json: rewrite de /api/(.*) a la función + fallback SPA para el router del cliente.
  • Subir las dependencias del backend al package.json raíz (ver aviso).
3

Config Supabase + Vercel (guiado paso a paso)

  • Supabase: verificar tablas (ya existen, el backend funciona), bucket garments público, copiar SUPABASE_URL + service_role key.
  • Vercel: importar el repo de GitHub, definir env vars en Production/Preview/Development, desplegar.
  • Dev local: .env del backend + VITE_API_URL=http://localhost:3000, correr ambos.
